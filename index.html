Prepared 30 Sep 2026 against the scope of work dated 29 Sep 2026 · RFP estimate 50 to 86 build hours, plan for 65 to 70

Current state: what the repos tell us

Both apps are single index.html files with no build step, which makes them easy to wrap but means state capture has to be added by hand. Findings from vondraak/eledcalc and vondraak/eledinstall as of today:

What this means for the build:

  1. Pricing is exposed today. Unit prices, markups and the cost side of the BOM ship to every visitor of the public Pages site. Putting the calc behind SSO with a Sales/Admin route rule is the first security win, and the Pages site must be turned off at cutover.
  2. ELEDCalc needs a real state API. Add getQuoteState() (inputs + ST + processor and H-series picks) and setQuoteState(). Store SNAP alongside it as the frozen result.
  3. Reloading an old quote must not reprice it. calc() reads the embedded catalog, so a reopened quote would silently use today's prices. Store the frozen SNAP and a catalog version; recalc only when the user creates a new version.
  4. ELEDInstall keys are positional. access.6.s means "the 7th item". Any template edit shifts data. Give every check item a stable key before any data goes into SQL.
  5. The RFP rules need fields ELEDCalc does not have. The catalog is 67 Ariel COB products, all IP 40 (indoor). There is no field for outdoor, transparent, foldable/hydraulic lift, mount type or delivery date. Add a small "Install attributes" card to the Quote tab.
  6. Free wins already exist. ELEDInstall's JSON export is a ready-made import format, and its sys.* fields map almost 1:1 to SNAP (size, resolution, weight, power, BTU, processor).

Target architecture

The three pages are static files; the API is the only thing that touches SQL or issues Blob links, so role checks and cost stripping live in one place. Browsers upload photos straight to Blob with a short-lived SAS the API hands out.

Data model

Normalize what gets searched and reported on; keep each app's full state as JSON so the pages reload exactly as saved. Every table carries CreatedAt, CreatedBy, UpdatedAt, UpdatedBy (Entra object id + UPN) and a rowversion for optimistic concurrency.

Search: a full-text catalog over QuoteVersions.SearchText (customer, project, product, notes) and Checklists job fields, plus ordinary indexes on status, dates and QuoteNumber. At roughly 5,000 records S0 is plenty.

Reporting: Power BI reads three views only, never base tables: rpt.vQuoteFacts, rpt.vInstallFacts, rpt.vDate. Views let the schema change without breaking the report.

API surface and auth

All endpoints live under /api, run as SWA managed Functions, and trust only the x-ms-client-principal header SWA injects. The API, not the page, decides what each role sees.

Auth setup

  • Entra app registration in the company tenant; SWA custom azureActiveDirectory provider with issuer login.microsoftonline.com/<tenantId>/v2.0. That single-tenant issuer is what blocks other tenants, and custom providers need the SWA Standard plan (already in the RFP).
  • App roles on the registration: Sales, Install, Admin. Assign via Entra groups. A rolesSource function maps the token's roles claim to SWA roles at sign-in.
  • staticwebapp.config.json: /calc/* requires sales or admin; /install/* and /portal/* require any of the three; /api/* requires authenticated; 401 redirects to /.auth/login/aad.
  • SQL connection: managed Functions cannot use a managed identity, so store a least-privilege SQL login (eled_app, db_datareader + db_datawriter + EXECUTE) in SWA app settings. If you later want passwordless, link a separate Function App (Standard feature) with managed identity.

Quote to checklist: rules engine

Approval builds the checklist in three steps inside one SQL transaction: copy the active template, map quote fields into it, then apply rules in priority order. The result records which rules fired, so the install team can see why an item is there.

Step 1: field mapping (fixed code, not rules)

Checklist field Source in quote
job.cust, job.addr Customer company, project site address
job.jobno QuoteNumber
job.dates Install attributes: delivery / install date
sys.model, sys.pitch, sys.ip SNAP.f model, pitch, IP rating
sys.size, sys.array, sys.res SNAP Wt x Ht, cabinet columns x rows, RW x RH
sys.weight, sys.power, sys.heat SNAP.kg, avgW / maxW, btu
sys.proc, sys.spares Selected processor or H-series config, spare lines
type chips Install attributes: environment, mount type

Step 2: rules as data. Conditions use JSON Logic (json-logic-js, a small, well-known library) over a flat facts object built from the quote. Actions are a closed list the engine understands.

{
  "name": "Outdoor installs",
  "priority": 100,
  "when": { "==": [ { "var": "environment" }, "Outdoor" ] },
  "then": [
    { "addItems": { "section": "elec", "block": "elc", "items": [
      { "key": "elc.out.gfci", "text": "Outdoor rated GFCI / weatherproof disconnect verified" },
      { "key": "elc.out.drain", "text": "Cabinet drainage and water ingress path inspected" } ] } },
    { "setChip": { "id": "type", "option": "Outdoor" } },
    { "markNA": { "items": [ "site.indoor-hvac" ] } }
  ]
}
Action Effect
addItems Append items (with stable keys) to a check block
markNA Pre-set items to N/A with note "Not applicable per rule"
setChip / setField Pre-fill a scope chip or field
addRows Add rows to a table block (e.g. extra crew roles for a lift)
addNote Insert a warning note at the top of a section

Facts available to conditions: environment, mountType, liftType, isTransparent, productModel, pitchMm, brightnessNits, cabinetCount, areaSqm, weightKg, maxPowerW, screenCount, hasHSeries, hasHdr, hasFiber. Adding a fact is a code change; adding or editing a rule is not.

Starter rules to define with the install team: outdoor or high brightness (3000 nits and up), foldable or hydraulic lift, transparent screen, large cabinet count (threshold TBD), fiber data path, flown / suspended mount, H-series processor.

Safety net: the admin page has a "preview" that runs the rules against any saved quote and shows the resulting checklist before a rule goes live.

  1. db/migrate.js (Node, mssql + @azure/identity) signs in with whatever az login or the GitHub OIDC step provides, so the same command works on your Mac and in CI:

    // node db/migrate.js eled-dev
const sql = require('mssql'); const fs = require('fs'); const path = require('path');
const db = process.argv[2];
const cfg = { server: 'sql-eled-platform.database.windows.net', database: db,
  authentication: { type: 'azure-active-directory-default' }, options: { encrypt: true } };
(async () => {
  const pool = await sql.connect(cfg);
  await pool.query(`IF OBJECT_ID('dbo.SchemaVersion') IS NULL
    CREATE TABLE dbo.SchemaVersion (Version int PRIMARY KEY, FileName nvarchar(200), AppliedAt datetime2 DEFAULT sysutcdatetime())`);
  const done = new Set((await pool.query('SELECT Version FROM dbo.SchemaVersion')).recordset.map(r => r.Version));
  const dir = path.join(__dirname, 'migrations');
  for (const f of fs.readdirSync(dir).filter(f => /^\d{3}_.*\.sql$/.test(f)).sort()) {
    const v = parseInt(f); if (done.has(v)) continue;
    const text = fs.readFileSync(path.join(dir, f), 'utf8');
    const batches = text.split(/^\s*GO\s*$/im).filter(b => b.trim());
    const noTx = /^--\s*no-transaction/m.test(text);        // full-text DDL cannot run in a transaction
    const tx = noTx ? null : new sql.Transaction(pool); if (tx) await tx.begin();
    for (const b of batches) await (tx ? new sql.Request(tx) : pool.request()).batch(b);
    await (tx ? new sql.Request(tx) : pool.request()).input('v', v).input('f', f)
      .query('INSERT dbo.SchemaVersion(Version, FileName) VALUES (@v, @f)');
    if (tx) await tx.commit(); console.log('applied', f);
  }
  await pool.close();
})().catch(e => { console.error(e); process.exit(1); });

SELECT q.QuoteId, q.QuoteNumber, q.Status, c.Company, v.ProductModel, v.PitchMm, v.TotalSell,
       CAST(q.CreatedAt AS date) AS CreatedDate,

JOIN dbo.Projects p ON p.ProjectId = q.ProjectId
JOIN dbo.Customers c ON c.CustomerId = p.CustomerId;
